# Retro: skmtc/publish-action#5, the CLI lock, the CI failure code and the promoted release

## 1. Summary

The ticket asked for three changes. First, a frozen Deno lockfile for the
default `@skmtc/cli` version, with a script to write it again and a CI check
that fails when it is stale. Second, a CI step that asserts the
`file-unreadable` error code. Third, `release.yml` on `released`. All three were
delivered in PR #6, squash-merged as 12d6d73, with CI green on three OSes. Run
`2026-10-29-pdtsq2`: 16m 24s wall clock (15m 13s agent), 19,225 input / 6.08M
cached / 77,355 output tokens, about $5.28, half the cost of #1's run. The most
costly step was implement ($2.82, 8m 15s), and it was worth it. The review found
one comment defect and nothing blocking.

## 3. Keep

- The ticket's Context gave checked outside facts (`--lock --frozen` works on
  2.9.8 and writes nothing to the cwd), traps and commands. The author spent no
  time on discovery. This is already the `orbital-ticket-prep` practice.
- Running `node dist/index.js` from an empty cwd with `RUNNER_TOOL_CACHE` set
  proved, before push, that the lock path does not resolve against the cwd.
  Write it in the README "Development" section.
- A `--frozen` run with no `--allow-net` exercises the CLI's read and parse
  paths with no hub call. It is a cheap check for lock gaps in dynamic imports.

## 4. Deferred

- `script/cli-lock.mjs`: there is no check that the local `deno` is
  `DENO_VERSION`. A maintainer who bumps the CLI with a newer local Deno can
  commit a lock that the action's Deno 2.9.8 refuses
  ([deferred 1](https://github.com/skmtc/publish-action/pull/6#issuecomment-6499499969)).
- `script/cli-lock.mjs`: it deletes `cli.lock` before `deno cache`, so a failed
  run leaves no lockfile. The maintainer meets this on a network error during
  `npm run cli-lock`. CI catches it through the cli-lock test (deferred 1).
- `__tests__/cli-lock.test.ts`: it does not assert `lock.version`, so a change
  of lock format shows up only in the three-OS job (deferred 1).
- `.github/workflows/release.yml`: promoting an older prerelease force-moves
  `v1` backwards. Every `@v1` user meets it when that happens, and the old
  trigger had the same gap
  ([deferred 2](https://github.com/skmtc/publish-action/pull/6#issuecomment-6499499969)).
- `src/args.ts` lock flags on `deno run`: a successful publish under `--frozen`
  was never run, because it needs a live hub token. The first real user publish
  is where a dynamic import missing from `cli.lock` would show up (implement
  summary).
- `released` firing for a promoted prerelease is not proven. The owner meets it
  at the first prerelease promotion.
- Windows cold install measured 16.5 s on PR #6, against the ticket's 15 s line.
  The compiled-binary follow-up stays the owner's decision.
